## 映像の選択と再エンコード

同じ取得経路の候補では上限内で最も高い解像度を優先します。既定値は 1080p です。解像度の判定には横動画の高さと縦動画の幅を使用します。1080p の設定では、1920×1080 と 1080×1920 がどちらも上限内です。上限を超える候補しかない場合は、上限に最も近い候補を選択し、縦横比を維持して縮小します。

選択した解像度で出力できる方式の優先順は、コピー、ハードウェアエンコード、ソフトウェアエンコードです。コピーの可否は、ブラウザーが受信できるコーデックと、解像度、フレームレート、映像ビットレートの設定で判定します。H.264 の B フレームによる表示順の並べ替えを検出した場合は、再生の途切れを回避するため再エンコードに切り替えます。

ハードウェアエンコーダーは起動時に試験し、配信開始時に実際の H.264 出力をブラウザーの受信条件と照合します。候補は macOS では VideoToolbox、Windows では Intel Quick Sync、NVIDIA NVENC、AMD AMF の順です。この順序はアプリの選択方針で、各方式の画質は未評価です。利用できる候補は FFmpeg のビルドと GPU ドライバーによって異なります。ソフトウェアでは最大 720p・30 fps の `libx264` と、VP8 を出力する `libvpx` が候補です。

フレームレートの上限が自動の場合、再エンコード時の上限は 30 fps です。映像ビットレートに 100〜12000 kbps を指定すると、その値を目標に再エンコードします。自動映像ビットレートは出力解像度とフレームレートから決定します。目標値は 720p・30 fps で 5 Mbps、1080p・30 fps で 8 Mbps、1080p・60 fps で 12 Mbps です。コピー時は入力の映像ビットレートで配信します。

yt-dlp が HLS の音声専用トラックのコーデック名を返さない場合も、そのトラックを音声の候補に含めます。

H.264 をコピーする場合は、各キーフレームにデコーダー設定を付与します。配信の途中で参加した視聴者が、受信したキーフレームから復号を開始できるようにするためです。

FFmpeg の NUT 出力は、`read` だけを公開するオブジェクトを介して PyAV に引き渡します。Windows のパイプは `seekable()` が真を返し、`seek` も読み取り位置を移動せずに成功するため、パイプをそのまま引き渡すと、PyAV が NUT の読み込み中にシークして `av.open` が失敗します。

**参照先** [FFmpeg の出力の読み取り](../src/backend/media/pipeline.py)、[入力選択](../src/backend/sources/yt_dlp_input.py)、[エンコーダーの選択と設定](../src/backend/media/video_encoding.py)、[YouTube の SDR エンコード推奨値](https://support.google.com/youtube/answer/1722171)

## 音声分離と障害復旧

音声を 48 kHz のモノラルに変換し、Inworld の `voice-isolator-v1-realtime` をストリーミングモードで使用します。先読みは 0 フレームです。背景音は原音から推定した声の成分を減算した結果です。声と背景音に個別のゲインを適用して合成し、Opus にエンコードします。音量の操作単位は dB で、既定値は声が 0 dB、背景音が −6 dB です。

**参照先** [Inworld Voice Isolator](https://huggingface.co/inworld/voice-isolator)

音声分離の停止が配信全体に波及しないよう、推論は別プロセスで実行します。準備中やタイムアウト時は原音で配信を継続します。その間は声と背景音の調整が停止し、分離の復旧後に再開します。MPS では初回とその直後の入力に加え、注意ウィンドウの切り替えまで事前に実行します。配信開始後の初回処理が応答期限を超え、原音に切り替わった事例への対策です。

通常のサーバー終了時は、音声分離プロセスも終了処理の対象です。親プロセスだけを SIGKILL で強制終了した場合は、応答を停止した子プロセスが残る可能性があります。

サーバーは 200 ms 分の音声ごとに推論を要求します。音声 1 ブロックの 200 ms に許容遅延の 120 ms を加え、応答期限を 320 ms とします。期限までに応答がない場合と、応答時に累積の処理遅延が 120 ms を超えた場合は原音に切り替えます。

音声分離ライブラリの状態空間ブロックは、`mamba_ssm` がない環境ではスキャンを 1 ステップずつ Python のループで実行します（`inworld/voice_isolation/scan.py` の `selective_scan`）。推論 1 回には、周波数方向に 46 ステップのスキャンと、前の状態を引き継ぐ時間方向の数ステップのスキャンが含まれます。CUDA では、アプリがこの関数を CUDA カーネルに置き換えます。カーネルは PyTorch に同梱された NVRTC で実行時にコンパイルするため、利用者の環境にコンパイラーは不要です。各スレッドが 1 チャネル分の状態をレジスタに保持し、ライブラリと同じ float32 の漸化式を計算します。このカーネルは、ライブラリの MPS 用 Metal カーネルを移植したものです。NVRTC でコンパイルできない場合は、ステップ数の対数に比例する回数の演算で計算する並列プレフィックススキャンを使用します。MPS では、ライブラリの Metal カーネルを使用します。

2026年11月24日に RTX 4070 Ti と Core i9-13900K の環境で計測した、40 ms 単位で推論した場合の 1 回あたりの値は次のとおりです。

| スキャンの実装 | 推論時間の中央値 | GPU の計算時間 | カーネル起動数 |
| --- | ---: | ---: | ---: |
| ライブラリ | 21〜28 ms | 約 6〜11 ms | 約 1950 |
| 並列プレフィックススキャン | 15〜17 ms | 約 6.3〜8.6 ms | 約 1030 |
| CUDA カーネル | 12〜13 ms | 約 3.1〜3.5 ms | 約 730 |

置き換え前は、スキャンが GPU の計算時間の約半分を占めていました。並列プレフィックススキャンはカーネル起動数を減らしますが、全ステップの状態をメモリに書き出すため、GPU の計算時間は減りません。推論時間の大半は CPU からのカーネル起動に費やされるため、処理時間は GPU の性能より CPU のシングルスレッド性能に左右されます。声の出力の差は、CUDA カーネルで SNR 約 56 dB、並列プレフィックススキャンで約 56〜64 dB でした。いずれも、入力に 10⁻⁶ の揺らぎを与えた場合のライブラリ自体の差と同程度です。初回のコンパイルには約 240 ms かかります。

並列プレフィックススキャンでは、ステップを 8 個または 16 個に区切り、区切りの間で状態を引き継ぐ方法も計測しましたが、カーネル起動数が増え、推論時間の中央値は 21〜36 ms で置き換え前と同等以上になりました。並列プレフィックススキャンでの配信中は、GPU のクロックが最大 2820 MHz まで上がり、消費電力が 60〜128 W になる場面がありました。置き換え前は 1185〜1740 MHz、約 50 W でした。GPU の処理が短い時間に集中し、ドライバーが高負荷と判断したためと考えられます。

推論 1 回の処理時間は、要求する音声の長さにほとんど依存しません。1 回の推論で起動するカーネル数が、音声の長さによらずほぼ一定のためです。CUDA カーネルを使用し、推論単位とライブラリの `block_frames` を合わせて計測した値は次のとおりです。

| 推論単位 | 推論時間の中央値 | 音声 1 秒あたりの処理時間 | 音声 1 秒あたりの GPU の計算時間 |
| ---: | ---: | ---: | ---: |
| 40 ms | 11〜13 ms | 約 300〜350 ms | 約 75〜154 ms |
| 80 ms | 約 13 ms | 約 170〜180 ms | 約 45 ms |
| 120 ms | 12〜13 ms | 約 110〜120 ms | 約 35 ms |
| 200 ms | 約 13 ms | 約 70 ms | 約 27 ms |

声の出力の差は、40 ms 単位に対して SNR 約 55 dB でした。音声と映像は元の PTS に基づいて送出するため、推論単位を長くしても音声と映像のずれは生じません。代わりに、再生開始とシーク後の遅延が推論単位の長さだけ増えます。

40 ms 単位で推論していたとき、処理中にタスクマネージャーに表示された GPU 使用率は約 70% でした。スキャンを置き換える前の推論時間の比率（27 ms ÷ 40 ms）とほぼ一致することから、この値は演算能力の使用率ではなく、GPU が処理中だった時間の割合と考えられます。VRAM の確保量は約 1.3 GB でした。CUDA 13.0 版の PyTorch が対応する GPU は、compute capability 7.5 の Turing 以降です。

200 ms 単位では、タスクマネージャーに表示されるワーカーの 3D 使用率が、約 30% の状態と 80〜100% の状態を十数秒ごとに繰り返します。2026年11月24日に 150 秒間計測した結果、両方の状態で `nvidia-smi` の SM 使用率（低い状態で約 24%、高い状態で約 33%）、SM クロック（約 300 MHz）、消費電力（約 44.5 W）、ワーカーの CPU 使用率（約 28%）はほぼ同じでした。タスクマネージャーが 91% を表示した時点で、SM 使用率が 0% だった場面もあります。この変動は Windows の集計上の見かけで、音声分離の負荷は一定です。集計が切り替わる原因は特定していません。GPU の負荷を確認する場合は、`nvidia-smi` の消費電力とクロックを参照します。

**参照先** [音声分離プロセス](../src/backend/media/audio_isolation.py)、[並列スキャンへの置き換え](../src/backend/media/parallel_scan.py)、[音声の合成](../src/backend/media/pipeline.py)

## 複数視聴とシーク

サーバーが同時に処理するのは 1 ストリームです。視聴者ごとに WebRTC 接続を確立するため、同じストリームを複数の端末で同時に視聴できます。配信の開始・停止、再生位置、声と背景音の音量は全視聴者で共有します。動画の品質、Firefox のログイン情報の使用、映像遅延はブラウザーごとに保存します。配信中の変更は、そのブラウザーから次回配信を開始した時点で全視聴者に適用されます。

配信中に参加した視聴者は、プレーヤー中央の再生ボタンを押下して視聴を開始します。通常動画の再生位置は、シークバーまたは10秒移動ボタンで変更できます。再生位置の変更と一時停止・再開は全視聴者に共通です。一時停止中はサーバーが動画の取得と処理を停止し、再開時は記録した再生位置を指定して処理を開始します。映像コピー時は、シークや再開の指定位置より前のキーフレームから再生する場合があります。シーク、一時停止、入力の再取得では WebRTC 接続を維持します。再開時には、送信時刻が引き続き単調に増加するように調整します。

映像と音声を別々に取得する通常動画で映像をコピーする場合、シークや再開時の音声の取得位置は、実際に再生を開始する映像のキーフレームに合わせます。音声が届く前に映像キューが満杯になるのを防ぐためです。

直接の HTTP(S) 入力では、FFmpeg に `-short_seek_size 32768` を指定します。FFmpeg 8.1 の HTTP プロトコルは、応答の残りのバイト数がこの閾値以下の場合、シーク時に新しい Range 要求を送信せず、残りを読み捨てます。閾値を指定しない場合、Windows の HTTPS では応答の残りが常に閾値以下と判定されます。32768 は、FFmpeg が入力の先読みに使用する既定の閾値と同じ値です。2026年11月24日に YouTube の 635 秒の動画で確認したところ、120 秒の位置へのシークは、指定しないと約 257 MB を読み捨てるため 40 秒以内に開始せず、指定すると約 0.3 秒で開始しました。HLS 入力はセグメント単位で取得するため、指定しません。

サーバーは、音量操作の処理を確認するための番号を WebSocket 接続ごとに管理し、状態通知の `mix_ack` に含めます。複数の操作をまとめて通知する場合も、ブラウザーは自分の操作の処理状況を確認できます。未処理の操作がある音量スライダーには、通知された値を適用しません。

iOS では、全画面表示の解除前後に WebKit が再生を一時停止することがあるため、プレーヤーは再開を試みます。解除時点ですでに 500 ms を超えて一時停止していた場合は、その状態を維持します。

配信の停止時は、FFmpeg の終了とメディア処理スレッドの終了を待ってから、次の配信を受け付けます。一時停止に伴う終了処理の途中で停止を要求した場合も、同じ順序で処理します。

Windows の Python 3.12 の asyncio では、UDP の送信中に `close()` を呼び出すと、送信の完了後も `connection_lost` が呼び出されず、トランスポートが閉じません。aiortc は WebRTC の接続を閉じる直前に RTCP BYE と DTLS の close_notify を送信し、続けて aioice が ICE の UDP ソケットを閉じて `connection_lost` を待機します。この送信が完了する前にソケットを閉じると、視聴者の接続の終了処理が完了せず、配信は停止処理中のまま終了しません。サーバーは起動時に asyncio のデータグラムトランスポートを修正し、送信の完了時にトランスポートが終了処理中であれば `connection_lost` を呼び出すようにします。

**参照先** [配信の管理](../src/backend/broadcast.py)、[メディアの中継とシーク処理](../src/backend/media/pipeline.py)、[ブラウザーの再生処理](../src/frontend/playback.mjs)、[音量とシークの操作](../src/frontend/broadcast-controls.mjs)

## 配信中の障害復旧

YouTube の入力が途切れた場合、取得先を更新して再接続します。配信中の復旧は最大3回、35秒までです。通常動画は中断位置付近、ライブ配信は取得できる最新のセグメントの1つ前から再開します。HTTP 403 やタイムアウトが発生した場合は、条件に応じて HLS と直接の HTTP(S) の取得経路を切り替えます。

ライブ配信の HLS 入力は、配信の開始時も再開時も最新のセグメントの1つ前から取得します（FFmpeg の `-live_start_index -2`）。FFmpeg はセグメント単位でまとめて受信し、その受信時刻は再生時刻に対して最大でセグメント1つ分ずれます。最新のセグメントから取得すると余裕がなく、次のセグメントの受信が遅れるたびに映像と音声が停止します。2026年11月26日に、セグメント長が5秒の YouTube のライブ配信で、再生時刻に対する受信の遅れを180秒間計測しました。最新のセグメントから取得した場合は開始後5〜30秒と100〜155秒に最大2.2秒遅れ、1つ前から取得した場合は常に再生時刻より2.9秒以上早く受信しました。この方式では、ライブ配信の遅延がセグメント1つ分増加します。

YouTube は自動アクセスと判定したリクエストを拒否する場合があります。Firefox のログイン情報を使用する設定を有効にすると、サーバーは yt-dlp に `--cookies-from-browser firefox` を指定します。対象はサーバープロセスを実行する OS ユーザーの Firefox プロファイルです。複数の候補がある場合は yt-dlp がプロファイルを選択します。

ログイン情報の取得に Firefox を採用した理由は、Windows で Chrome の起動中に yt-dlp が Cookie データベースを読み取れない場合があるためです。

**参照先** [動画情報の取得処理](../src/backend/sources/yt_dlp_input.py)、[Windows で Chrome 起動中に発生する Cookie の読み取りエラー](https://github.com/yt-dlp/yt-dlp/issues/7271)

操作用の WebSocket だけが切断された場合は、WebRTC を維持したまま WebSocket を再接続します。WebRTC も切断され、配信が継続していれば、ブラウザーから WebRTC の接続を再試行します。再接続の猶予は、サーバーが最後の視聴者の切断を検知してから15秒間です。

**参照先** [入力の復旧処理](../src/backend/broadcast.py)、[WebSocket の再接続](../src/frontend/signaling.mjs)、[WebRTC の再接続](../src/frontend/playback.mjs)

## 映像と音声の同期

2026年11月23日に macOS のヘッドレス Chrome で、同期マーカー付きの 720p・30 fps の素材を再生して計測しました。映像のマーカーは `requestVideoFrameCallback` で、音声のマーカーは受信した `MediaStream` を接続した `AudioWorklet` で検出しました。条件ごとに5回実行し、各回5組のマーカーの時刻差から中央値を算出しました。表の値は、条件ごとに各回の中央値を集計した中央値です。正の値は音声の遅れを示します。

| 映像の処理方式 | 原音 | 音声分離 |
| --- | ---: | ---: |
| コピー | 39.2 ms | 39.1 ms |
| VideoToolbox | 39.2 ms | 44.6 ms |

音声分離ありの条件は MPS で処理し、原音への切り替えはありませんでした。条件ごとの中央値は約39〜45 ms で、各回の中央値の範囲は条件間で重なりました。計測範囲はブラウザー内の映像と音声の時刻差です。配信全体の遅延や、Bluetooth イヤホンから音が出る時刻まで含むズレは未計測です。

Bluetooth イヤホンなどで音声が遅れて聞こえる環境に対応するため、配信開始時の映像遅延を共有設定にしました。中継処理で映像パケットの送出時刻とタイムスタンプを調整します。補正はコピーと再エンコードの両方に適用できます。別の単回試験では設定値を 0 ms から 120 ms に変更した結果、音声と映像の時刻差はコピーで +23.0 ms から −79.3 ms、VideoToolbox で +22.3 ms から −72.0 ms に変化しました。負の値は音声の先行を示します。この試験もブラウザー内の時刻差を計測しました。

映像遅延の初期状態はオフで、有効時の既定値は 200 ms です。有効にした場合は 0〜500 ms の整数を指定します。

ステータスに表示する値はサーバーが適用した映像遅延です。対象の出力機器で同期テスト動画を再生すると、実際のズレを確認できます。動画の URL は映像遅延のヒントからコピーできます。

**参照先** [映像遅延を適用する中継処理](../src/backend/media/pipeline.py)

## リソース使用量の表示

ステータスにはアプリの音声分離の処理負荷、CPU 使用率、メモリ使用量、GPU 使用率、GPU メモリ使用量を表示します。サーバーは 2 秒ごとに値を集計し、状態通知で各ブラウザーに送信します。アプリのプロセスはサーバーと、その子孫である音声分離プロセスと FFmpeg です。アプリのプロセスの値を特定できない場合は、項目名に「(PC全体)」または「(Mac全体)」を付けて PC 全体または Mac 全体の値を表示し、値を取得できない項目は表示しません。

CPU 使用率は全論理コアに対する割合で、メモリ使用量は各プロセスの常駐メモリの合計です。どちらも psutil で取得します。Windows の GPU 使用率は NVML のプロセスごとの SM 使用率で、取得できない場合は GPU 全体の使用率を表示します。タスクマネージャーと同じ「GPU Engine」カウンターは、実際の負荷と食い違う場合があるため使用しません。Windows の GPU メモリ使用量は「GPU Process Memory」カウンターの専用メモリの値で、CUDA の初期化分と FFmpeg の使用分を含みます。macOS の GPU 使用率は、プロセスごとの値を取得する公開の方法がないため、`ioreg` から Mac 全体の値を取得します。macOS の GPU メモリ使用量は、音声分離プロセスが推論の応答に付与する MPS の確保量です。

音声分離の処理負荷は、推論の要求から応答までの時間を音声の長さで割った値の移動平均です。応答期限に達した要求は平均に含まれません。表示は 2 秒ごとに更新し、5 秒以上推論がない場合は表示しません。表示が 100% 未満でも、応答期限または累積の処理遅延の上限を超えると原音に切り替わります。

Windows の Python 3.12 では `time.monotonic()` の分解能が約 15.6 ms と 1 回の推論時間の計測には粗すぎるため、処理時間は `time.perf_counter()` で計測します。

2026年11月24日に Apple M4 Pro の Mac で、1080p・60 fps の HLS 入力を VideoToolbox で再エンコードし、MPS で音声を分離する配信を観測しました。約51秒間の 24 サンプルで、画面の GPU 使用率（Mac 全体）は中央値 70%、範囲 42〜94% でした。

Metal System Trace では、プロセスごとに GPU の実行区間の重複を除き、記録時間に対する割合を算出しました。

| 記録時間 | Python の計算処理 | Metal の実行区間全体 |
| --- | ---: | ---: |
| 16.2 秒 | 28% | 55% |
| 9.2 秒 | 33% | 63% |

2 回目の記録では、Python のプロセス ID が音声分離ワーカーと一致しました。映像専用エンジンと視聴端末の GPU 使用率は未計測です。

**参照先** [リソース使用量の集計](../src/backend/resource_usage.py)、[音声分離プロセス](../src/backend/media/audio_isolation.py)

## 起動環境と接続設定

macOS と Windows の起動スクリプトは、Python 3.12、FFmpeg、Deno、依存パッケージを `.runtime` に配置します。次回以降は既存の環境を使用し、起動のたびに yt-dlp の更新を確認します。初回は Hugging Face から音声分離モデルも取得します。推論の実行先は、Windows では CUDA、macOS では MPS です。MPS で FFT が動作しない macOS のバージョンでは、CPU で推論します。`--device cpu` のように起動オプションを指定すると、推論の実行先を選択できます。

CPU では音声分離の処理がリアルタイムに追い付かないため、Windows の起動スクリプトは NVIDIA の GPU を必須とし、CUDA 13.0 版の PyTorch を配置します。Core i9-13900K で 40 ms 分の音声の推論時間を計測した結果、1 スレッドで約 232 ms、最速の 8 スレッドでも約 67 ms でした。CUDA 13.0 版を採用したのは、R580 以降のドライバーで動作し、R595 以降を要する CUDA 13.2 版より対応するドライバーの範囲が広いためです。PyTorch が CUDA を使用できない場合、起動スクリプトはサーバーを起動せずに終了します。

macOS の起動スクリプトは Apple Silicon を必須とします。Intel Mac で利用できる PyTorch は 2.2 系で、音声分離ライブラリは 2.6 未満の PyTorch では MPS を選択しないため、Intel Mac では CPU で推論します。前述の Windows の計測結果から、CPU の推論はリアルタイムの処理に追い付かないと判断しました。

起動スクリプトは必須の依存関係を準備した後で、yt-dlp の更新を試みます。更新先に接続できない場合も、必要な依存関係がそろっていれば既存の yt-dlp で起動します。

**参照先** [macOS の起動スクリプト](../start.mac.command)、[Windows の起動スクリプト](../start.ps1)、[起動環境の準備とサーバーの引数](../src/backend/bootstrap_runtime.py)

通常の起動スクリプトは `127.0.0.1:48763`、別端末用は `0.0.0.0:48763` で待ち受けます。別端末用のスクリプトはすべての IPv4 インターフェースを対象とし、LAN や VPN 内のアドレスを接続先として表示します。`--host` で待受先の IPv4 アドレス、`--port` でポートを指定できます。たとえば `192.168.1.10:48764` に指定する場合は、リポジトリのフォルダーで次のコマンドを実行します。

```sh
./start.mac.command --host 192.168.1.10 --port 48764
```

```powershell
.\start.win.cmd --host 192.168.1.10 --port 48764
```

## ZIP 版の更新

サーバーは、起動時から終了まで `.runtime/server-<ポート番号>.lock` をロックします。ポート番号が異なれば、同じフォルダーから別のサーバーを起動できます。各サーバーが処理するストリームは 1 つです。

サーバーはポート別のロックを取得する間、更新と共通のロックを保持します。更新スクリプトは共通のロックを取得し、全ポートのロックが解除されていることを確認してから GitHub に接続します。更新が終了するまで、新たなサーバーは起動できません。

更新スクリプトは ZIP の SHA-256、版番号、配布ファイルの一覧を検証します。旧版と新版の一覧に含まれるファイルを対象とし、`.runtime` と配布対象外のファイルを保持します。差し替え前に旧版のファイルを退避します。更新が中断された場合は、更新スクリプトの再実行時に旧版のファイルを復元してから更新を再試行します。

**参照先** [更新処理](../src/backend/update.py)、[起動と更新の排他制御](../src/backend/install_lock.py)

### 正式リリースと更新用 ZIP

[`VERSION`](../VERSION) にリリース番号を記載し、ファイルの追加や削除を [`release-files.txt`](../release-files.txt) に反映してください。そのコミットに `VERSION` と一致する `v` 付きのタグを指定して、GitHub で正式リリースを公開してください。

GitHub Actions は公開イベントを受けて版番号と配布ファイルの一覧を検証し、タグのコミットから `oshigoe.zip` を作成してリリースに添付します。更新スクリプトは GitHub が添付ファイルに記録した SHA-256 を使用します。

このワークフローでは、公開後もファイルを添付できるリリースを使用します。

**参照先** [ZIP の添付ワークフロー](../.github/workflows/release-zip.yml)、[GitHub の変更不可リリース](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
